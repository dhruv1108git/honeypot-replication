### Issue Analysis: Cache Key Doesn't Include Sample Count

When self-consistency was added in commit `b65d1f8`, the code was updated to:
1. Check if the cached replies match the requested sample count
2. If not, treat it as a cache miss

However, the cache key itself doesn't include the sample count, which means:
- If a request is first rated with `samples=1`, it's stored in the cache
- Later, if the same request is rated with `samples=3`, the cache will find the entry (same key) but see that the reply count (1) doesn't match the requested count (3)
- This triggers a cache miss, and the request is re-rated
- The new result (3 replies) is stored under the same key, overwriting the previous entry

This works functionally but is inefficient:
1. It causes unnecessary cache misses when the sample count changes
2. It overwrites potentially useful cache entries

The correct approach would be to include the sample count in the cache key, so different sample counts get different cache entries. This would:
1. Prevent overwriting of cache entries
2. Allow sharing of cache between runs with different sample counts
3. Make the cache behavior more predictable

Let me check if the temperature should also be included. When `samples > 1`, the `sample_temperature` is used instead of the base `temperature`. So both the sample count and the temperature should be part of the cache key.
